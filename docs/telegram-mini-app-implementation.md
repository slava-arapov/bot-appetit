# Telegram Mini App: реализация экранов и бизнес-API

Дизайн-документ. Зафиксирован по итогам обсуждения 2026-10-01; все четыре среза реализованы (см. «Статус реализации» в конце). Дополняет `docs/telegram-mini-app.md` (что делает приложение) и `docs/telegram-mini-app-dev-env.md` (каркас). Здесь — как это строится поверх каркаса и в каком порядке. Реализация — отдельным шагом.

## Понимание задачи

- Что строим: бизнес-слой Mini App поверх готового каркаса — эндпоинты `settings`, `pantry`, `profile`, `summary` и экраны Настройки, Pantry, Профиль, плюс живые подписи на хабе.
- Зачем: быстро править структурированную память тапом, без диалога с LLM.
- Для кого: `approved`-пользователи бота (десятки человек). Разработчик один, фронтенд-бэкграунд.
- Ключевые ограничения: API живёт в процессе бота и использует общее соединение `aiosqlite`; авторизация только по `initData`; Vue 3 + TS без Pinia; цвета только из `themeParams`.
- Не делаем: историю блюд, онбординг в Mini App, деплой/HTTPS/туннель, удаление текстовых команд `/pantry` и `/profile` (на них ставится `TODO`).

## Допущения

1. **Список покупок = статус `to_buy`.** В `pantry_items.status` три значения: `have`, `low`, `to_buy`. Отдельной таблицы списка покупок нет.
2. **`out` — только сигнал в `memory_update`.** От LLM `out` по-прежнему означает «товар закончился, удалить». В БД и в API `out` не хранится; старые строки с `out` мигрируются в `to_buy`.
3. **Поток из чата.** Закончилось → товар удалён (`out`) → бот в том же ответе спрашивает про список покупок → при согласии следующим шагом LLM шлёт `to_buy`. «Купил» из чата → `have`.
4. **Точечные операции вместо load→save.** Записи pantry и теги профиля имеют `id`; API и бот меняют данные точечными SQL-операциями. Это снимает гонку между тапом в Mini App и правкой от бота.
5. **`servings`/`cooking_time`.** Mini App пишет канонические значения (`"4"`, `"15"/"30"/"60"/"any"`). Старые свободные строки разбираются на чтении, при неудаче поле пустое. В промпт и текстовый `/profile` значения уходят человекочитаемыми строками. Схема БД не меняется.
6. Дубликаты (название товара, тег внутри `kind`) определяются без учёта регистра в Python через `casefold()`: `lower()` в SQLite не понимает кириллицу.
7. Захардкоженный список техники для чеклиста лежит на фронте; кастомные пункты берутся из `profile_tags`.
8. Нагрузка небольшая, задержки локальные; безопасность: все запросы ограничены `user_id` из проверенного `initData`, чужие `id` дают 404; валидация — pydantic-модели.
9. Тесты: pytest на store и эндпоинты, Vitest на логику экранов.

## Финальный дизайн

### Общая инфраструктура (появляется в срезе «Настройки»)

- `useSnackbar` — один снекбар в `App.vue`. Ошибка: не исчезает, кнопка «Повторить». Удаление: «Удалено · Отменить», 4–5 с.
- Обёртка `haptic.success()` / `haptic.error()` над `HapticFeedback` (без API на клиенте — no-op); те же заглушки в mock.
- `BackButton` подключается в роутере: скрыта на хабе, в разделах показана и ведёт на `/`.
- `apiFetch` учится пустому ответу (204) — понадобится для `DELETE`.
- Токены стилей: к `--tg-*` добавляются производные (фокус, ошибка, радиусы, отступы, минимальная тач-цель `44px`); цвета только из `themeParams`.

### Срез 1: Настройки

Данные (`memory/store.py`):
- `get_settings(user_id)` → `{servings: int | None, cooking_time: "15"|"30"|"60"|"any"|None}`. `servings` — первое число из строки в диапазоне 1–8, иначе `None`; `cooking_time` — число из 15/30/60 или «не важно», иначе `None`.
- `set_settings(user_id, *, servings=..., cooking_time=...)` обновляет только переданные поля через `INSERT … ON CONFLICT DO UPDATE` по `profiles`, не затрагивая `onboarding_*` и контекст.
- `describe_servings()` / `describe_cooking_time()` для промпта агента и текстового `/profile` («4 порции», «до 30 минут», «время не важно»). Перед реализацией прочитать `agent/chef.py` и `/profile` и найти все места вывода этих полей.

API: `GET /api/settings`; `PATCH /api/settings` — любое подмножество полей (`servings`: int 1–8, `cooking_time`: `Literal`), пустое тело → 422, в ответе обновлённые значения.

Экран (`SettingsView.vue`, `useSettings`): скелетон при загрузке; степпер `servings` (`−`/значение/`+`, 44×44, `disabled` на границах, `None` показывается как «—», первое `+` ставит 2); segmented control `cooking_time` как `radiogroup`; автосохранение: оптимистичное обновление → `PATCH` → haptic при успехе, откат и снекбар «Повторить» при ошибке.

Тесты: нормализация старых строк (таблица), round-trip `PATCH`, 422 на `servings=9` и неизвестный `cooking_time`, 401 без `initData`; Vitest — границы степпера, откат, дебаунс, выбор сегмента.

### Срез 2: Pantry

Данные:
- `list_pantry` (с `id`), `add_pantry_item`, `update_pantry_item(id, …)`, `delete_pantry_item(id)`; все проверяют владельца, чужой `id` → «не найдено» (404).
- Дубликат по названию (`casefold()`) обновляет существующую запись.
- Миграция `UPDATE pantry_items SET status='to_buy' WHERE status='out'` в `init_db()`, идемпотентная; перед этим проверить на тестовой БД.
- `apply_pantry_update` для бота переписан на точечные операции: `out` — удалить; `to_buy` — создать/перевести в `to_buy`; `have`/`low` — обновить статус, срок годности, количество.

Бот и промпт:
- `agent/chef.py`: правило «закончилось → `out`, затем спроси про список покупок; согласился → `to_buy`; купил → `have`»; в рецептах `to_buy` считается отсутствующим продуктом.
- `notify_expiring` пропускает `to_buy`.
- Текстовый `/pantry` рисует секцию «Нужно купить»; на `/pantry` и `/profile` — `TODO` на будущее удаление.

API: `GET/POST /api/pantry`, `PATCH/DELETE /api/pantry/{id}`; `name` 1–80 символов после trim, `status: Literal["have","low","to_buy"]`, `quantity`, `expiry_date` (ISO). `EXPIRY_WARNING_DAYS` отдаётся API, не дублируется на фронте.

Экран:
- Секции «Мало» → «Нужно купить» → «Есть»; пустые секции скрыты; пустое состояние всего экрана с кнопкой «+».
- Чип статуса по кругу `have → low → to_buy → have`, оптимистично, с haptic.
- Удаление: свайп влево + кнопка «Удалить» в bottom sheet редактирования (открывается тапом по карточке); «Отменить» пересоздаёт запись.
- Bottom sheet добавления: название обязательно, `MainButton` «Добавить» активна только при непустом названии.
- Подсветка срока годности по `EXPIRY_WARNING_DAYS`.

Тесты: все ветки `apply_pantry_update`, кириллический дедуп, чужой `id` → 404, миграция; Vitest — цикл чипа, undo.

### Срез 3: Профиль

Данные:
- `list_tags(user_id)` по четырём `kind` с `id`; `add_tag(user_id, kind, value)` (trim, 1–40 символов, дедуп внутри `kind` через `casefold()`, повтор возвращает существующий тег); `remove_tag(user_id, tag_id)` с проверкой владельца.
- `save_profile` пересоздаёт теги (онбординг), поэтому `id` нестабильны; `apply_memory_update` переводится на `add_tag`/`remove_tag`. Перед реализацией прочитать `apply_memory_update`, чтобы не сломать контракт `memory_update`.

API: `GET /api/profile` → `{restrictions, equipment, likes, dislikes}` (элементы `{id, value}`); `POST /api/profile/tags {kind, value}`; `DELETE /api/profile/tags/{id}`.

Экран:
- Группы: restrictions → equipment → likes → dislikes; пустая группа показывает «Пока ничего не добавлено».
- Теги — чипы, ×-кнопка с зоной 44×44; ввод по Enter и видимой кнопке «+»; удаление со снекбаром «Отменить» (пересоздаёт тег).
- Equipment — чеклист: захардкоженный список ∪ кастомные теги; включение = `add_tag`, выключение = `remove_tag`. Выключенный кастомный пункт остаётся на экране до перезагрузки и затем исчезает — следствие решения «кастомный неотличим от дефолтного».
- 404 по устаревшему `id` → перезапрос `GET /api/profile`.

Тесты: `add_tag` и дедуп на кириллице, чужой `id`, `apply_memory_update` на тегах; Vitest — чеклист (включение, выключение, кастомный пункт), перезапрос по 404.

### Срез 4: Хаб

- `GET /api/summary` → `{pantry: {low, to_buy, expiring}, profile: {restrictions, likes, …}, settings: {servings, cooking_time}}` (готовые числа для подписей, например «2 товара заканчиваются, 3 купить»).
- Хаб: скелетон, при ошибке карточки без подписи, переходы работают. Отладочный вывод `user_id` из `/api/me` убирается.
- Тесты: суммы в `/api/summary`, поведение хаба при ошибке запроса.

### Документация и проверки

- Обновить `CLAUDE.md`: статус `to_buy` и «`to_buy` и есть список покупок» (вместо «список покупок не хранится отдельно»), новые эндпоинты, смысл `out` как сигнала «удалить».
- UX-проверки скилла `ui-ux-pro-max` прогоняются на каждом срезе: тач-цели 44px, контраст в light/dark, haptic, `prefers-reduced-motion`, фокус и клавиатура.

## Риски

- Контракт `memory_update`: LLM может перепутать `out` и `to_buy`. Смягчение: явные примеры в промпте и тесты разбора.
- Переписывание `apply_pantry_update` и обработки тегов меняет поведение бота. Смягчение: тесты на все ветки до рефакторинга.
- Миграция `out → to_buy` затрагивает данные. Смягчение: идемпотентность и проверка на тестовой БД до прод-старта.
- Нестабильные `id` тегов. Смягчение: 404 → перезапрос списка на фронте.

### Отступления от исходного дизайна

- `out` → `to_buy` как статус позиции списка покупок (решение пользователя, поток из чата описан в допущениях).
- Кнопка «Добавить» внутри формы, а не `MainButton`.
- Для ошибки без осмысленного повтора (дубль названия, 409) кнопка «Понятно» вместо «Повторить».
- Цвета статусов запасов (`--status-have/low/buy`) — смысловые, не из `themeParams`; для тёмной темы переопределяются через `data-scheme` на корне документа.

### Известные ограничения

- **Быстрые тапы по чипу статуса.** Второй тап, пока первый запрос в пути, при ошибке первого откатит значение к устаревшему.
- **Включить и сразу выключить пункт техники.** Пока создание тега ещё в пути, `DELETE` уйдёт с временным отрицательным `id` и получит 404; фронт тихо перезапросит профиль, но пункт может остаться отмеченным.
- **`id` тегов нестабильны между сессиями:** онбординг и сбросы по-прежнему идут через `save_profile`, который пересоздаёт теги. Фронт переживает это через 404 → перезапрос.
- **Поведение LLM.** Различение `out` («убрать») и `to_buy` («в покупки») держится на тексте промпта; проверено только тестами на сам текст, не на реальных диалогах.
- **Список техники** в чеклисте (`webapp/src/utils/profile.ts`) набросан разработчиком и ждёт правки владельца.
- **Миграции при старте бота** меняют данные: `out → to_buy` в запасах и приведение тегов профиля к нижнему регистру со слиянием дублей (`memory/db.py:_lowercase_tags`). Слияние необратимо: из «Духовка» и «духовка» остаётся один тег. Перед первым запуском на проде стоит скопировать `data/bot.db`.
