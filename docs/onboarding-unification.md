# Единый формат порций, времени и техники: онбординг и Mini App

Дизайн-документ. Зафиксирован по итогам обсуждения 2026-10-02. Реализация — отдельным шагом.

## Понимание задачи

- Онбординг в чате пишет в БД свободный текст, а Mini App ждёт структурированные значения: степпер порций 1–8, пресеты времени `15/30/60/any` и чек-лист техники. Прод-значения, не попавшие в формат, Mini App показывает пустыми.
- Приводим к единому виду **порции, время готовки и технику**: в онбординге эти три шага становятся инлайн-кнопками, как в Mini App.
- Вкусы, антипатии и ограничения остаются свободным текстом (в Mini App они уже свободные теги).
- Существующие пользователи (прод: 13 профилей, 8 с тегами) получают разовую миграцию данных. Повторно онбординг никто не проходит.
- Non-goals: чистка мусорных тегов («нет», «Всё ем»), слияние синонимов техники («духовой шкаф» и «духовка»), рассылка пользователям, перенос онбординга в Mini App, кнопки для кухонь, аллергенов и диет.

### Что показал прод (`bot-prod.db`)

- Порции: «1, иногда 2», «на 1», «2», «4» — `normalize_servings` берёт первое число, потерь почти нет.
- Время: «до 30 минут», «30 мин», «Не важно» распознаются; «1 час», «Не более 1 часа», «Как можно меньше» — нет.
- Техника: 58 тегов, в основном «духовка», «блендер», «мультиварка», «микроволновка», но есть и «кастрюля 5 л», «сковорода 26 см», «вакууматор».
- `memory_update` от LLM не пишет `servings` и `cooking_time`: они меняются только онбордингом и Mini App.

## Допущения

1. Масштаб — десятки пользователей, один процесс, один SQLite; производительность не критична.
2. Новых требований к приватности и доступности нет.
3. Скрипт миграции запускается вручную, делает бэкап `bot.db` и идемпотентен.
4. Список техники живёт в одном месте на бэкенде (`config.py`).
5. Схема SQLite не меняется; `onboarding_step` сохраняет смысл «индекс+1 заданного вопроса», поэтому пользователи посреди анкеты продолжат с того же места.

## Подходы

- **A. Типизированные шаги онбординга (выбран).** Шаги получают тип `text/choice/multiselect`, хендлер рисует клавиатуру и принимает нажатие либо текст через `normalize_*`.
- B. Кнопки поверх текстового онбординга: хендлер сам собирает текст из нажатий и отдаёт в старый `run_onboarding`. Минимум правок, но валидация размазана, формат не гарантирован.
- C. Онбординг как отдельный модуль-автомат (`bot/onboarding.py`). Чище всего, но рефакторинг избыточен для масштаба проекта (YAGNI).

## Дизайн

### 1. Шаги и данные

`ONBOARDING_QUESTIONS` и `ONBOARDING_FIELDS` в `agent/chef.py` заменяются списком шагов:

```python
@dataclass(frozen=True)
class Step:
    field: str      # likes | dislikes | restrictions | servings | cooking_time | equipment
    question: str
    kind: Literal["text", "choice", "multiselect"]
```

- `text`: likes, dislikes, restrictions — как сейчас (разбор по запятым).
- `choice`: servings и cooking_time. Варианты берутся из `SERVINGS_RANGE` и `COOKING_TIME_PRESETS` (`memory/store.py`), подписи кнопок — «15 мин», «30 мин», «1 час», «Не важно».
- `multiselect`: equipment. Список `EQUIPMENT_OPTIONS` переезжает из `webapp/src/utils/profile.ts` в `config.py`.

`run_onboarding` возвращает `StepView(text, keyboard | None)` вместо строки. Остальные места, где он вызывается без ответа (`/start`, одобрение заявки, сброс), отправляют `view.text` вместе с `view.keyboard`. На шагах `choice` в `profiles.servings` и `profiles.cooking_time` пишется строка пресета (`"2"`, `"30"`, `"any"`), как это делает `set_settings` из Mini App.

### 2. Клавиатуры, колбэки и текстовый ввод

- Callback-данные (лимит 64 байта): `onb:servings:3`, `onb:time:30`, `onb:eq:<индекс>`, `onb:eq:other`, `onb:eq:done`. Для техники в callback идёт индекс из `EQUIPMENT_OPTIONS`.
- Раскладка: порции — две строки по четыре кнопки (1–8); время — одна строка из четырёх; техника — по две кнопки в ряд, ✅ на выбранных, внизу «✏️ Другое» и «Готово».
- После выбора на `choice` сообщение редактируется в «✓ 3 порции» без клавиатуры и приходит следующий шаг.
- Новый `CallbackQueryHandler` с `pattern=r"^onb:"` в `main.py`, рядом с approval и reset; проходит гейт `_require_approved`. Колбэк сверяет шаг с состоянием профиля: устаревшая кнопка отвечает `answer("Этот вопрос уже неактуален")` и ничего не пишет.
- Выбор техники хранится в `context.user_data["onb_equipment"]` (набор индексов). При потере состояния (рестарт) шаг показывается заново без галочек; в БД пишется только итог по «Готово».
- «Другое»: бот просит написать техники через запятую, ставит `user_data["onb_awaiting_custom"]`; следующий текст разбирается по запятым, приводится к нижнему регистру через `normalize_tag`, добавляется к выбору, клавиатура показывается снова. Нажатие любой кнопки сбрасывает флаг.
- Текст вместо кнопки на `choice`: `normalize_servings` / `normalize_cooking_time`. Распознано — принимается как нажатие. Не распознано — «Выбери вариант кнопкой 👇», та же клавиатура, `onboarding_step` не двигается.
- Текст на шаге техники трактуется как «Другое».

### 3. API списка техники, Mini App и миграция

- `GET /api/profile` дополняется полем `equipment_options: list[str]`. `EquipmentChecklist.vue` берёт список из ответа; `DEFAULT_EQUIPMENT` в `profile.ts` удаляется. Пока профиль не загружен, чек-лист не рисуется (скелетон уже есть).
- `normalize_cooking_time` расширяется: «1 час», «час», «1 ч», «60 мин», «60 минут», «не более 1 часа», «до часа» → `60`; «до 30 минут», «30 мин» → `30`; «не важно» / «неважно» → `any`. Число принимается, только если совпадает с пресетом; «40 минут» и «полтора часа» не округляются. «Как можно меньше» остаётся `None`.
- Скрипт `migrate_normalize_settings.py` (по образцу `migrate_to_sqlite.py`): по умолчанию dry-run с таблицей «user_id: было → станет»; `--apply` сначала копирует `bot.db` в `bot.db.bak-<дата>`, затем пишет нормализованные значения в `profiles` только там, где результат не `None` и отличается от текущего. Нераспознанные значения не трогаются и выводятся отдельным блоком. Повторный запуск ничего не меняет.
- Скрипт сначала прогоняется в dry-run на `bot-prod.db`; сам файл не изменяется. Схема SQLite, теги техники в проде и эндпоинты `PATCH /api/settings` и `POST /api/profile/tags` не меняются.

### 4. Ошибки, крайние случаи и тесты

Крайние случаи:
- устаревшая кнопка и двойной тап: колбэк идемпотентен, при `onboarding_step`, ушедшем вперёд, — ветка «неактуально»;
- `edit_message_text` падает (`BadRequest`): следующий шаг уходит новым сообщением;
- пользователь не `approved`: гейт `_require_approved`;
- пустое «Готово» на технике: пустой список, как и сегодня при пустом ответе;
- `/start` посреди анкеты: через `current_onboarding_question` показывается текущий шаг с клавиатурой, выбор галочек сбрасывается;
- `/reset onboarding` дополнительно сбрасывает состояние онбординга в `user_data`.

Тесты (pytest, без LLM):
- `normalize_cooking_time` на реальных значениях из прода и граничных случаях;
- `choice`: нажатие пишет пресет; валидный текст принимается; невалидный повторяет клавиатуру и не двигает шаг;
- техника: переключение, «Другое», «Готово», потеря `user_data`;
- устаревший и двойной колбэк не пишут в БД;
- скрипт миграции: dry-run не меняет, `--apply` идемпотентен, бэкап создаётся;
- `GET /api/profile` отдаёт `equipment_options`;
- фронт (vitest): `EquipmentChecklist` берёт список из пропсов.

Порядок реализации: 1) `normalize_*` и константы, 2) шаги и `StepView`, 3) колбэки и `main.py`, 4) API и фронт, 5) скрипт миграции, 6) обновление `CLAUDE.md`.

## Decision Log

| # | Решение | Альтернативы | Почему |
|---|---|---|---|
| 1 | Унифицируем только порции, время и технику | Всё кнопками; онбординг в Mini App | Вкусы, антипатии и ограничения в Mini App уже свободные теги; расхождение только в трёх полях. Минимальное изменение, которое его убирает |
| 2 | Существующие значения: расширить `normalize_cooking_time` + разово переписать однозначные в БД | Только расширить распознавание; плюс рассылка пользователям | Одно время и разовая миграция дают чистую БД без ручного участия пользователей; рассылка — лишний канал и риск |
| 3 | Техника: мультивыбор + «Другое» + «Готово», список в `config.py`, фронт получает его из API | Продублировать список; мультивыбор без «Другое» | Один источник правды; нестандартная техника («казан», «вакууматор») уже есть в проде и не должна теряться |
| 4 | Текст на шагах с кнопками: пробуем `normalize_*`, при неудаче просим нажать кнопку | Всегда требовать кнопку; принимать любой текст | В БД попадает только валидное значение, но пишущих текстом не раздражаем |
| 5 | Подход A: типизированные шаги | Кнопки поверх текста; отдельный автомат | Решает задачу без избыточного рефакторинга; `normalize_*` и `set_settings` переиспользуются |
| 6 | Выбор техники хранится в `context.user_data`, в БД пишется итог | Хранить промежуточный выбор в БД | Потеря при рестарте безвредна (шаг показывается заново), схема не меняется |
| 7 | В callback идёт индекс техники, не название | Название в callback | Лимит 64 байта, кириллица, проще и безопаснее |
| 8 | «Плита» остаётся одним пунктом списка | Разделить на газовую/электрическую/варочную панель | Решение пользователя; детализация не нужна текущим рецептам |
| 9 | `memory_update` не нормализуется для servings/cooking_time | Нормализовать при записи | LLM эти поля не пишет, проверено по коду |
| 10 | Незавершённая анкета у существующих пользователей продолжается с того же шага | Сбрасывать онбординг | `onboarding_step` не меняет смысл, миграция схемы не нужна |

## Риски

- Состояние мультивыбора техники теряется при рестарте процесса. Последствие: пользователь заново ставит галочки.
- Нераспознанные прод-значения («Как можно меньше») остаются пустыми в Mini App, пока пользователь сам не выберет значение в настройках.
- Изменение сигнатуры `run_onboarding` затрагивает все места вызова (`/start`, одобрение, сброс). Закрывается тестами.
- Список техники в `config.py` теперь контракт между ботом и Mini App: переименование пункта не переименует уже сохранённые теги.
